# 정보처리기사 실기 — 05. 인터페이스 구현

> 이 챕터는 **모듈과 시스템이 맞닿는 지점**을 다룸.
> 03단원(통합 구현)이 시스템 사이의 연계였다면, 여기는 **요구사항 정의부터 구현·검증까지의 전 과정**임.
> 무엇을 주고받을지 식별하고 → 방법을 명세하고 → 구현하고 → 예외·보안을 처리하고 → 검증함.
>
> 📌 **미들웨어 솔루션의 종류(특히 WAS·TP-Monitor·ORB)** 와
> **인터페이스 구현 검증 도구(xUnit·STAF·NTAF 등)** 가 단답형으로 자주 나옴.

## (1) 시스템 인터페이스 요구사항 분석

### 시스템 인터페이스

**독립적으로 떨어져 있는 시스템들끼리 서로 연동해 상호 작용**하기 위한 접속 방법이나 규칙.

### 시스템 인터페이스 요구사항

개발할 시스템과 연계할 **내·외부 시스템 간의 연동에 관한 요구사항**.

**구성 항목** ⭐

| 항목 | 내용 |
|---|---|
| **인터페이스 이름** | 해당 인터페이스의 명칭 |
| **연계 대상 시스템** | 연계할 내·외부 시스템의 이름 |
| **연계 범위 및 내용** | 연계를 통해 주고받는 데이터의 범위와 업무 내용 |
| **연계 방식** | EAI, 웹 서비스, API 등 사용할 연계 방식 |
| **송신 데이터** | 연계할 데이터의 개별 항목과 데이터 형식 |
| **인터페이스 주기** | 연계 주기(실시간, 일 배치, 월 배치 등) |
| **기타 고려사항** | 보안, 오류 처리 등 추가로 고려할 사항 |

### 요구사항 분석 절차

```mermaid
flowchart LR
    A[요구사항 선별] --> B[요구사항 관련 자료 준비] --> C[요구사항 분류] --> D[분석 및 명세서 구체화] --> E[요구사항 확인 및 검증]
```

| 단계 | 내용 |
|---|---|
| **요구사항 선별** | 요구사항 명세서에서 **인터페이스와 관련된 요구사항을 선별** |
| **관련 자료 준비** | 정의서, 명세서 등 분석에 필요한 **자료를 준비** |
| **요구사항 분류** | 기능/비기능, 시스템/사용자 등 **기준에 따라 분류** |
| **분석 및 명세서 구체화** | 다이어그램·표를 이용해 **명확하게 표현** |
| **요구사항 확인 및 검증** | 이해관계자가 **검토**하고 **승인** |

## (2) 인터페이스 요구사항 검증

### 요구사항 검증

인터페이스 요구사항 명세서가 **정확하고 완전하게 작성되었는지 확인**하고,
이해관계자들의 **요구사항을 올바르게 반영**했는지 검토하는 활동.

### 검증 절차

```mermaid
flowchart LR
    A[검토 계획 수립] --> B[검토 및 오류 수정] --> C[베이스라인 설정]
```

| 단계 | 내용 |
|---|---|
| **검토 계획 수립** | 검토 기준과 방법, 참여자, 일정 등을 정함 |
| **검토 및 오류 수정** | 요구사항 명세서를 검토하고 발견된 오류를 수정 |
| **베이스라인 설정** | 검토가 완료된 요구사항을 **변경 관리의 기준선(Baseline)** 으로 설정 |

> **베이스라인(Baseline)** : 정식으로 검토되고 합의되어 이후 개발의 기준이 되며,
> **변경을 통제해야 할 시점의 기준**이 되는 산출물.

### 요구사항 검증 방법 ⭐⭐

| 방법 | 설명 |
|---|---|
| **동료 검토**<br>(Peer Review) | 요구사항 명세서 **작성자가 직접 설명**하고 동료들이 이를 들으며 결함을 발견 |
| **워크스루**<br>(Walk Through) | 검토 회의 전에 **명세서를 미리 배포**해 사전 검토한 후 짧은 검토 회의를 통해 결함을 발견 |
| **인스펙션**<br>(Inspection) | 요구사항 명세서 **작성자를 제외한 다른 전문가들**이 명세서를 확인하며 결함을 발견 |

> 💡 **누가 설명하느냐**로 구분함. 동료 검토는 **작성자가 설명**, 인스펙션은 **작성자를 뺀** 전문가들이 검토.

### 요구사항 검증 항목(체크리스트)

| 항목 | 확인 내용 |
|---|---|
| **완전성**(Completeness) | 요구사항이 **누락 없이** 기술되었는가 |
| **일관성**(Consistency) | 요구사항 간 **충돌이나 모순**이 없는가 |
| **명확성**(Unambiguity) | 모든 이해관계자가 **하나로 이해**할 수 있는가 |
| **기능성**(Functionality) | '어떻게(How)' 보다 **'무엇(What)'** 에 중점을 두었는가 |
| **검증 가능성**(Verifiability) | 요구사항이 **검증 가능한가** |
| **추적 가능성**(Traceability) | 요구사항의 **출처와 관련 시스템을 추적**할 수 있는가 |
| **변경 용이성**(Easily Changeable) | 요구사항 명세서의 **변경이 쉬운가** |

## (3) 인터페이스 시스템 식별

### 인터페이스 시스템 식별

**개발할 시스템과 연계할 내·외부 시스템을 정확히 파악**하는 작업.

| 구분 | 내용 |
|---|---|
| **개발할 시스템 식별** | 개발하려는 시스템의 **구성, 목적, 역할**을 명확히 함 |
| **내·외부 시스템 식별** | 연계할 시스템의 **이름, 위치, 담당자, 시스템 코드** 등을 식별 |
| **인터페이스 목록 작성** | 식별된 인터페이스를 **목록으로 정리** |

### 인터페이스 시스템 식별 항목

- 시스템 **이름과 코드**
- 시스템 **역할**과 **담당 조직·담당자**
- 시스템 간 **연계 방향**(송신/수신)

## (4) 송·수신 데이터 식별

### 송·수신 데이터

인터페이스를 통해 **송·수신되는 데이터**로,
**규격화된 표준 형식**에 따라 전송됨.

### 데이터의 종류 ⭐

| 종류 | 설명 |
|---|---|
| **인터페이스 표준 항목** | 시스템 공통부와 거래 공통부로 나뉨. **인터페이스 송·수신 시스템을 연계하는 데 사용되는 항목** |
| **송·수신 데이터 항목** | 실제 업무 수행에 필요한 **데이터 항목** |
| **공통 코드** | 시스템에서 **공통으로 사용하는 코드** 정보 |

**인터페이스 표준 항목**

| 구분 | 포함 정보 |
|---|---|
| **시스템 공통부** | 시스템 간 연계 시 필요한 **공통 정보** — 인터페이스 ID, 전송 시스템 정보, 서비스 코드 정보, 응답 결과 정보, 장애 정보 |
| **거래 공통부** | 업무 처리를 위해 **각 시스템에서 필요한 정보** — 직원 정보, 승인자 정보, 기기 정보, 매체 정보 |

## (5) 인터페이스 방법 명세화

### 인터페이스 방법 명세화

내·외부 시스템이 **연계 시 이용하는 방법을 문서로 명확히 기술**하는 것.

### 명세화 항목

| 항목 | 내용 |
|---|---|
| **시스템 연계 기술** | DB Link, API, 웹 서비스, EAI 등 **어떤 기술로 연계할지** |
| **인터페이스 통신 유형** | **단방향, 동기(Synchronous), 비동기(Asynchronous)** |
| **인터페이스 처리 유형** | **실시간(Real Time), 지연 처리, 배치(Batch)** |
| **인터페이스 발생 주기** | 매일, 매주, 매월 등 |
| **인터페이스 데이터 표준** | 데이터 형식과 규칙 |

### 통신 유형 ⭐

| 유형 | 설명 |
|---|---|
| **단방향** | 송신 시스템에서 **일방적으로 데이터를 보내고 응답을 받지 않음** |
| **동기**(Synchronous) | 요청을 보내고 **응답이 올 때까지 대기**함 |
| **비동기**(Asynchronous) | 요청을 보낸 후 **응답을 기다리지 않고** 다른 작업을 수행하다가 나중에 결과를 받음 |

### 처리 유형

| 유형 | 설명 |
|---|---|
| **실시간**(Real Time) | 요청과 동시에 처리 |
| **지연 처리** | 데이터를 모았다가 **일정 시간 후** 처리 |
| **배치**(Batch) | **정해진 주기**에 대량의 데이터를 일괄 처리 |

## (6) 미들웨어 솔루션

### 미들웨어(Middleware)

**미들(Middle)** 과 **소프트웨어(Software)** 의 합성어로,
운영체제와 응용 프로그램, 또는 서버와 클라이언트 **사이에서 다양한 서비스를 제공**하는 소프트웨어.

- 표준화된 인터페이스를 제공해 **데이터 교환에 일관성**을 부여함.
- 통신 제공 방법이나 기능에 따라 여러 종류로 나뉨.

### 미들웨어의 종류 ⭐⭐

| 종류 | 설명 |
|---|---|
| **DB**(DataBase) | **데이터베이스 벤더에서 제공하는 클라이언트에서 원격의 DB 와 연결**하기 위한 미들웨어. 2-Tier 아키텍처라고 함 |
| **RPC**<br>(Remote Procedure Call, 원격 프로시저 호출) | 응용 프로그램의 프로시저를 사용해 **원격 프로시저를 마치 로컬 프로시저처럼 호출**하는 방식 |
| **MOM**<br>(Message Oriented Middleware, 메시지 지향 미들웨어) | **메시지 기반의 비동기형 메시지를 전달**하는 방식. **온라인 업무보다는 이기종 분산 데이터 시스템의 데이터 동기를 위해** 사용 |
| **TP-Monitor**<br>(Transaction Processing Monitor, 트랜잭션 처리 모니터) | **항공기나 철도 예약 업무 등 사용자 수가 증가해도 빠른 응답 속도를 유지**해야 하는 업무에 사용되는 미들웨어 |
| **ORB**<br>(Object Request Broker, 객체 요청 브로커) | **객체 지향 미들웨어**로 **코바(CORBA)** 표준 스펙을 구현한 미들웨어 |
| **WAS**<br>(Web Application Server) | **정적인 콘텐츠를 처리하는 웹 서버와 달리 동적인 콘텐츠를 처리**하기 위해 사용되는 미들웨어. HTTP 세션 처리를 위한 웹 서버 기능과 트랜잭션 관리 기능을 제공 |

> 📌 **핵심 대응 관계**
> - **TP-Monitor** → 항공기·철도 **예약**처럼 빠른 응답이 필요한 업무
> - **ORB** → **CORBA** 표준, 객체 지향
> - **MOM** → **비동기** 메시지, 이기종 데이터 **동기화**
> - **WAS** → **동적** 콘텐츠

## (7) 모듈 간 공통 기능 및 데이터 인터페이스 확인

### 인터페이스 설계서

**시스템 사이의 데이터 교환 및 처리를 위해 각 시스템의 교환 데이터 및 관련 업무,
연계 방식 등을 정의한 문서**.

| 구분 | 내용 |
|---|---|
| **시스템 인터페이스 설계서** | 시스템의 **인터페이스 목록**과 각 인터페이스의 **상세 데이터 명세**를 정의한 문서 |
| **정적·동적 모형을 통한 설계서** | 시스템 구성 요소 간의 **정적·동적 관계**를 다이어그램으로 표현한 문서 |

### 모듈 세부 설계서 ⭐

모듈의 **구성 요소와 세부적인 동작 등을 정의**한 설계서.

| 설계서 | 내용 |
|---|---|
| **컴포넌트 명세서** | 컴포넌트의 **개요, 내부 클래스의 동작, 인터페이스를 통해 외부와 통신하는 명세** 등을 정의 |
| **인터페이스 명세서** | 컴포넌트 명세서의 항목 중 **인터페이스 클래스의 세부 조건 및 기능**을 정의 |

### 모듈 간 공통 기능 확인

- 인터페이스 설계서에서 **각 모듈이 공통으로 사용하는 기능**을 확인함.
- 로그인, 권한 체크, 로그 기록, 암·복호화 등이 대표적임.

### 모듈 간 데이터 인터페이스 확인

- 모듈 간 **주고받는 데이터의 형식, 데이터 타입, 길이, 필수 여부**를 확인함.
- 인터페이스 명세서의 **데이터 항목**을 기준으로 확인함.

## (8) 인터페이스 데이터 표준 확인

### 인터페이스 데이터 표준

모듈 간 인터페이스에 사용되는 **데이터의 형식을 표준화**하는 것.

### 데이터 표준 확인 절차

```mermaid
flowchart LR
    A[데이터 표준 확인] --> B[인터페이스 설계서 확인] --> C[데이터 표준 검토] --> D[데이터 표준 정의]
```

| 단계 | 내용 |
|---|---|
| **데이터 표준 확인** | 송·수신 시스템 사이의 데이터 표준을 **인터페이스 설계서를 통해 확인** |
| **인터페이스 설계서 확인** | 인터페이스 **목록과 상세 데이터 명세**를 확인 |
| **데이터 표준 검토** | 송·수신 데이터 항목과 인터페이스 표준 항목을 **비교·검토** |
| **데이터 표준 정의** | 최종적으로 **표준 항목을 확정**하고 문서화 |

## (9) 인터페이스 기능 구현 정의

### 인터페이스 기능 구현 정의

앞서 정의한 **인터페이스 기능을 실제로 구현하기 위한 방법을 정의**하는 것.

### 정의 절차

```mermaid
flowchart LR
    A[컴포넌트 명세서 확인] --> B[인터페이스 명세서 확인] --> C[일관된 인터페이스 기능 구현 정의] --> D[정의된 인터페이스 기능 구현 정형화]
```

| 단계 | 내용 |
|---|---|
| **컴포넌트 명세서 확인** | 컴포넌트의 **개요, 내부 클래스의 동작, 인터페이스 통신 명세**를 확인 |
| **인터페이스 명세서 확인** | 컴포넌트 명세서 중 **인터페이스 클래스의 세부 조건과 기능**을 확인 |
| **일관된 인터페이스 기능 구현 정의** | 인터페이스의 기능 구현을 **일관성 있게 표준화**해 정의 |
| **정형화** | 정의한 내용을 **의사 코드(Pseudo Code)나 다이어그램**으로 정형화 |

## (10) 인터페이스 구현

### 인터페이스 구현

송·수신 시스템 간의 데이터 교환 및 처리를 실현해 주는 **작업을 의미**함.

### 구현 방법 ⭐⭐

| 방법 | 설명 |
|---|---|
| **데이터 통신을 이용한 인터페이스 구현** | 애플리케이션 영역에서 **데이터 포맷을 인터페이스 대상으로 전송**하고, 수신 측에서 이를 **파싱(Parsing)해 해석**하는 방식. 주로 **JSON, XML** 형식의 데이터를 사용 |
| **인터페이스 엔티티를 이용한 인터페이스 구현** | 인터페이스가 필요한 시스템 사이에 **별도의 인터페이스 테이블(엔티티)을 두어** 상호 연계하는 방식 |

### JSON(JavaScript Object Notation) ⭐

**속성-값 쌍(Attribute-Value Pairs)** 으로 이루어진 **데이터 객체를 전달하기 위해**
사람이 읽을 수 있는 텍스트를 사용하는 **개방형 표준 포맷**.

- 비동기 처리에 사용되는 **AJAX** 에서 XML 을 대체해 널리 사용됨.
- XML 보다 **가볍고 파싱이 빠름**.

```
{
  "회원번호": "M001",
  "이름": "김하늘",
  "대출도서": ["B1024", "B2048"],
  "연체여부": false
}
```

### AJAX(Asynchronous JavaScript and XML)

자바스크립트를 사용해 클라이언트와 서버 간에 **XML 데이터를 주고받는 비동기 통신 기술**.

- 전체 페이지를 새로 고치지 않고도 **페이지의 일부만 변경**할 수 있음.

## (11) 인터페이스 예외 처리

### 예외 처리

인터페이스 실행 시 오류가 발생할 경우 **오류의 원인과 내용을 인지**할 수 있도록
사용자에게 알리고, **오류로 인한 데이터 손상 등을 방지**하는 것.

### 데이터 통신을 이용한 인터페이스에서의 예외 처리 ⭐

**송신 측 예외 처리**

| 원인 | 처리 방안 |
|---|---|
| 데이터 생성·전송 실패 | 전송 실패를 **로그로 기록**하고 **재전송** 시도 |
| 데이터 형식 오류 | 오류 데이터를 **별도로 관리**하고 담당자에게 통보 |
| 네트워크 장애 | **일정 시간 대기 후 재전송**, 지속 시 담당자 통보 |

**수신 측 예외 처리**

| 원인 | 처리 방안 |
|---|---|
| 데이터 수신 실패 | 수신 실패를 **로그로 기록**하고 송신 측에 **오류 응답** |
| 파싱(Parsing) 오류 | 잘못된 형식의 데이터를 **격리**하고 오류 코드 반환 |
| 데이터 처리 실패 | **트랜잭션을 롤백**하고 오류 내용을 기록 |

### 인터페이스 엔티티를 이용한 인터페이스에서의 예외 처리

인터페이스 테이블에 **오류 코드와 오류 내용을 저장하는 컬럼**을 두고,
오류 발생 시 해당 컬럼에 기록해 담당자가 확인하도록 함.

| 처리 대상 | 방법 |
|---|---|
| **송신 시스템** | 데이터 입력 실패 시 **트랜잭션 종료 및 오류 로그 기록** |
| **수신 시스템** | 데이터 읽기·반영 실패 시 **오류 코드를 인터페이스 테이블에 기록** |

## (12) 인터페이스 보안

### 인터페이스 보안

인터페이스는 **시스템 모듈 간 통신 및 정보 교환을 위한 통로**이므로
**충분한 보안 기능을 갖추지 않으면 시스템 모듈 전체에 악영향**을 줄 수 있음.

### 인터페이스 보안 취약점 분석

- **네트워크 영역** : 스니핑(Sniffing) 등 **데이터 탈취**
- **애플리케이션 영역** : 소스 코드의 **보안 취약점**
- **데이터베이스 영역** : **데이터 자체의 유출**

### 계층별 보안 기능 적용 ⭐

| 영역 | 적용 방법 |
|---|---|
| **네트워크 영역** | 인터페이스 송·수신 간 **암호화된 채널을 이용**해 데이터를 전송.<br>**IPSec**(네트워크 계층), **SSL/TLS**(전송 계층), **S-HTTP**(응용 계층) 적용 |
| **애플리케이션 영역** | **소프트웨어 개발 보안 가이드**를 참조해 코드 상의 보안 취약점을 보완 |
| **데이터베이스 영역** | **데이터베이스 암호화 알고리즘**을 적용. 개인정보·민감정보 컬럼을 암호화 |

### 데이터베이스 암호화 기법

| 기법 | 설명 |
|---|---|
| **API 방식** | **애플리케이션 레벨**에서 암호 모듈(API)을 적용 |
| **Plug-In 방식** | **DB 레벨**에서 암호화 모듈을 적용 |
| **TDE**(Transparent Data Encryption) | DBMS 가 제공하는 **투명한 데이터 암호화** 기능을 이용 |
| **Hybrid 방식** | **API 방식과 Plug-In 방식을 혼합**해 사용 |

## (13) 인터페이스 구현 검증

### 인터페이스 구현 검증

인터페이스가 **정상적으로 동작하는지 확인**하는 것.

**인터페이스 단위 기능과 시나리오를 기반으로 하는 통합 테스트**가 필요함.

### 인터페이스 구현 검증 도구 ⭐⭐

| 도구 | 설명 |
|---|---|
| **xUnit** | Java(**JUnit**), C++(**CppUnit**), .Net(**NUnit**) 등 **다양한 언어를 지원하는 단위 테스트 프레임워크** |
| **STAF** | **서비스 호출 및 컴포넌트 재사용** 등 다양한 환경을 지원하는 테스트 프레임워크. 각 테스트 대상 분산 환경에 **데몬을 사용**하며, 테스트 대상 프로그램을 통해 테스트를 수행하고 결과를 통합해 자동화하는 검증 도구 |
| **FitNesse** | **웹 기반**의 테스트 케이스 설계·실행·결과 확인 등을 지원하는 테스트 프레임워크 |
| **NTAF** | **FitNesse 의 협업 기능**과 **STAF 의 재사용 및 확장성**을 통합한 **NHN(네이버)** 의 테스트 자동화 프레임워크 |
| **Selenium** | **다양한 브라우저 및 개발 언어를 지원**하는 **웹 애플리케이션** 테스트 프레임워크 |
| **watir** | **Ruby** 를 사용하는 애플리케이션 테스트 프레임워크 |

> 📌 **NTAF = FitNesse(협업) + STAF(재사용·확장성)**, 개발사는 **NHN**. 이 조합이 자주 나옴.

### 인터페이스 감시 도구 ⭐

인터페이스의 **동작 상태를 감시(모니터링)** 하는 도구.

- 상용 **APM(Application Performance Management/Monitoring)** 도구를 사용해
  동작 상태를 확인할 수 있음.
- 대표적인 오픈 소스 APM 으로 **스카우터(Scouter)**, **제니퍼(Jennifer)** 등이 있음.

| 도구 | 설명 |
|---|---|
| **스카우터**(Scouter) | 애플리케이션 및 OS 등 다양한 자원에 대한 **모니터링 기능을 제공**하는 오픈 소스 APM |
| **제니퍼**(Jennifer) | 애플리케이션의 **개발부터 운영까지 전 단계에 걸친 성능을 모니터링**하고 분석해 주는 APM |

### 인터페이스 구현 검증 절차

```mermaid
flowchart LR
    A[검증 도구 및 감시 도구 선정] --> B[인터페이스 목록 확인] --> C[테스트 케이스 작성] --> D[테스트 실행] --> E[결과 검증 및 오류 조치]
```

### 인터페이스 오류 확인과 처리

| 단계 | 내용 |
|---|---|
| **오류 발생 인지** | 화면 알림, 로그, 이메일·SMS 등으로 오류 발생을 확인 |
| **오류 원인 분석** | 로그와 모니터링 정보를 통해 원인을 파악 |
| **오류 조치** | 원인에 따라 데이터·프로그램·환경을 수정 |
| **결과 기록** | 조치 내용을 **오류 관리 대장**에 기록 |

**오류 상황 통보 방법**

- 화면에 **오류 메시지** 표시
- 오류 **로그 기록**
- 관리자에게 **이메일·SMS 발송**
